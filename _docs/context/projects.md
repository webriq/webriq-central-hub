# Projects, display IDs, Files deep links, classification nav

Moved verbatim from CLAUDE.md. Read before working in this area.

- **`projects` table** (renamed from `customer_projects` in migration 025) holds project-level metadata (`name`, `project_type`, `status`, `external_project_id`, `sanity_project_id`, `github_repo`, `dedicated_developers`, `customer_product_id`) keyed by `customer_id`. A customer can have multiple projects. `project_type` is one of: `Content Site | Ecommerce (B2C) | Ecommerce (B2B) | Custom App`. The column `project_name` was renamed to `name` — use `.from("projects")` and `row.name`, never `row.project_name`. `zoho_project_id` was renamed to `external_project_id` in migration 066 (task 142) now that Zoho is being decommissioned — same semantics (Zoho's project ID, written by `createZohoProject()`/Zoho sync/import/export flows), just a generic name. Do not confuse this with `_zoho_project_id` (underscore-prefixed) — an unrelated, still-Zoho-specific convention used only inside `zoho-export`/`zoho-import` routes to tag raw Zoho project IDs onto exported records for import-time correlation; that one is untouched. `projects` also has a `project_id` column (migration 066, format changed in migration 088/task 187) — a public-facing, human-readable ID (`<last 8 chars of customer_id>-PROJ-<2-digit incremental sequence, e.g. 01, 02, 03>`, auto-generated by a DB trigger on insert — the sequence is per-customer, counts that customer's projects in creation order, and is derived from the max existing sequence number for that customer rather than a row count, so a deleted project's number is never reused) that is **display-only**; the UUID `id` column remains the routing key in every URL/route param, unchanged — **except** two deliberate, scoped exceptions where the `[projectId]` URL segment holds `project_id` itself, not the UUID: `/v2/portfolio-tracker/[projectId]` (task 150), and `/v2/projects/[projectId]` plus its nested `/v2/projects/[projectId]/tasks/[taskId]` route (task 188 changed the `projectId` segment to `project_id`; task 190 subsequently changed the nested route's `taskId` segment too, from `tasks.id` to `tasks.display_id` — migration 089/task 189's human-readable task ID — so both segments on this nested route are now display values, neither is the UUID). Every other route in the app keeps the UUID-as-routing-key rule above. The portfolio-tracker route's Wizard step state is addressed via `?phase=&deliverable=` query params (1-based deliverable index within the phase), not a nested route segment — see `_wizard-step-params.ts`.

- **Project Files tab deep links** (task 359) — `/projects/{<slug>,legacy}/[projectId]/files` accepts `?folder=<folder uuid>` (opens that folder) and `?file=<asset uuid>` (opens the asset's own `folder_id`, then auto-opens its preview modal). `?file=` carries no companion `?folder=` on purpose — the folder is derived from the asset, so a moved file doesn't break the link. Unresolvable ids fall back to the Files root. Folder navigation syncs the URL via `window.history.replaceState`, **not** `router.replace` — both Files pages are `force-dynamic`, so a Next navigation would re-run the server component on every folder click. The copy URLs are built from `usePathname()`, never from the `projectId` prop: on v2 the `[projectId]` segment is the display `project_id` while the component receives the UUID. **Do not confuse this with the Onboarding Workspace's scheme** (`_workspace-url-params.ts`), which addresses folders by root-to-leaf *name* path (`?parent_folder=`/`?sub_folder_lN=`) because it maps deliverables onto folders; the workspace shares the same presentational `FilesTab` but omits the task-359 props, so it shows no Copy URL actions.

- **Projects routing + classification navigation** (tasks 361, 473, 474) — every v2 project URL carries its classification slug: listing `/projects/<slug>`, status report `/projects/<slug>/status-report` (scoped to that classification, no Classification filter), project pages `/projects/<slug>/<projectId>/…` (display `project_id`), plus `/projects/new`, `/projects/import`, `/projects/legacy`. Slugs + helpers (`classificationTabHref`, `classificationStatusReportHref`, `projectHref`, `projectResolverHref`) live in `src/app/(hub)/projects/_classification-tabs.ts`, whose `Record<Classification, ClassificationTabId>` map makes a new classification a compile error until it gets a slug. **Reserved slugs** (static folders win over `[classification]`): `legacy`, `v2`, `new`, `import`, plus `unclassified`, which is valid **only** on project pages (projects with no classification) and has no listing or sidebar link. A project page accepts **any** of the project's own classification slugs; another slug redirects (same sub-path + query) to its first one — `[classification]/[projectId]/layout.tsx` via `_project-shell.ts`. Links inside a project use `useProjectsBase()` (`_use-projects-base.ts`, `useParams`) so you stay in the classification you came from; outside a `[classification]` route it falls back to the resolver. **`/projects/v2` holds no pages**: `projects/v2/[[...rest]]/page.tsx` redirects old and classification-less links (saved notification/mention URLs, dashboards, timer, time logs, orders → `projectResolverHref()`; `?tab=` listing links; old status-report/new/import paths). The sidebar's "Projects" group has one link per classification plus Legacy; active state is a plain path-prefix match (task 414's project-context workaround was removed in 474), so a multi-classified project highlights the classification in its URL. There is deliberately **no "All" link and no per-classification counts**. `_listing-shell.tsx` is title-only. Classification membership is the union `customer_products.classifications[] ∪ customer_products.classification` (three row shapes coexist; `PATCH /api/v2/projects/[projectId]/classification` keeps both in sync via `mergeClassificationUpdate()`), so a multi-classified project appears under **every** classification it carries. The `customer_products!inner` + `referencedTable` `.or()` join in `_load-list-data.ts` excludes classification-less Zoho import noise by construction (task 272).


- **"General" task list** (task 486, migration 183, written-not-applied) — a task never has a null `tasklist_id` (checklist rows excepted). A `tasks` trigger (insert, and update of `tasklist_id`/`project_id`) puts a null list into the project's General list via `ensure_general_tasklist()` (`SECURITY DEFINER`, created on demand). So a deleted or cleared list, and a merge-wizard "skip list", all land in General. General = `lower(trim(name))='general'` and `source <> 'programme'`, with or without a phase (`is_general_tasklist()`; Zoho Generals usually sit under a milestone). 183 merged duplicate Generals per project into one (no phase first, then oldest). Nothing prevents new duplicates afterwards. It is flagged `is_default` only in projects that had no default (Zoho defaults kept). A `project_deliverables` trigger blocks renaming or deleting it (project cascade delete and deleting an extra duplicate allowed). The Tasks listing folds orphan tasks into General (`generalTasklistId()` in `_shared/_list-view.tsx`). Task 430's column rename must update both triggers.

- **Tasks listing tree + moves** (task 487, migration 184, written-not-applied) — the Tasks tab list view is Phase (`milestones`) › Group (`tasklists`, phase = `tasklists.milestone_id`) › root task › subtasks. The pure model lives in `_shared/_tasks/_task-tree.ts` (`buildPhases`, `groupResolver`, `phaseKey`; `generalTasklistId()` moved here). Phase-less lists render under a trailing "No phase" band, and a project with no milestones shows lists only. Programme phases keep their programme number in the `PHASE n` chip (the `milestones` view hides programme Phase 1). Drag-and-drop uses dnd-kit sensors with an own hit test (`data-drop-id="task|group|phase:<id>"`, zones in `_move-rules.ts`). Keyboard moves are custom (`_use-keyboard-move.ts`), and "Move to…" in the row menu is the non-drag path. **All task moves go through `POST /api/v2/tasks/[id]/move`** → `move_task()` RPC (service-role-only, called with `adminClient` after `getTaskEditPermission`). It moves the subtree's `tasklist_id`/`milestone_id`/`depth` and fails on a cycle or past depth 5. Editors may move anywhere; status-only assignees may only reorder siblings. Never add `tasklist_id`/`parent_task_id` to `PATCH /api/v2/tasks/[id]`. Before 184 the route returns 503 and the client falls back to sibling reorder via `PATCH { position }`. Lists: `PATCH /api/v2/tasklists/[id] { position?, milestone_id? }` (pm/admin/super_admin; a phase change also re-points the list's tasks' `milestone_id`). Phases reorder via the existing milestones PATCH. Starting a drag switches the sort to "Manual order" (`position`). Comment counts come from `project_task_comment_counts()` (184); `user_preferences.tasks_density` (184, needs 182) stores the row-density choice. Task 430's rename must update `move_task` and both new routes.
