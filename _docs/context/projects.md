# Projects, display IDs, Files deep links, classification nav

Moved verbatim from CLAUDE.md. Read before working in this area.

- **`projects` table** (renamed from `customer_projects` in migration 025) holds project-level metadata (`name`, `project_type`, `status`, `external_project_id`, `sanity_project_id`, `github_repo`, `dedicated_developers`, `customer_product_id`) keyed by `customer_id`. A customer can have multiple projects. `project_type` is one of: `Content Site | Ecommerce (B2C) | Ecommerce (B2B) | Custom App`. The column `project_name` was renamed to `name` — use `.from("projects")` and `row.name`, never `row.project_name`. `zoho_project_id` was renamed to `external_project_id` in migration 066 (task 142) now that Zoho is being decommissioned — same semantics (Zoho's project ID, written by `createZohoProject()`/Zoho sync/import/export flows), just a generic name. Do not confuse this with `_zoho_project_id` (underscore-prefixed) — an unrelated, still-Zoho-specific convention used only inside `zoho-export`/`zoho-import` routes to tag raw Zoho project IDs onto exported records for import-time correlation; that one is untouched. `projects` also has a `project_id` column (migration 066, format changed in migration 088/task 187) — a public-facing, human-readable ID (`<last 8 chars of customer_id>-PROJ-<2-digit incremental sequence, e.g. 01, 02, 03>`, auto-generated by a DB trigger on insert — the sequence is per-customer, counts that customer's projects in creation order, and is derived from the max existing sequence number for that customer rather than a row count, so a deleted project's number is never reused) that is **display-only**; the UUID `id` column remains the routing key in every URL/route param, unchanged — **except** two deliberate, scoped exceptions where the `[projectId]` URL segment holds `project_id` itself, not the UUID: `/v2/portfolio-tracker/[projectId]` (task 150), and `/v2/projects/[projectId]` plus its nested `/v2/projects/[projectId]/tasks/[taskId]` route (task 188 changed the `projectId` segment to `project_id`; task 190 subsequently changed the nested route's `taskId` segment too, from `tasks.id` to `tasks.display_id` — migration 089/task 189's human-readable task ID — so both segments on this nested route are now display values, neither is the UUID). Every other route in the app keeps the UUID-as-routing-key rule above. The portfolio-tracker route's Wizard step state is addressed via `?phase=&deliverable=` query params (1-based deliverable index within the phase), not a nested route segment — see `_wizard-step-params.ts`.

- **Project Files tab deep links** (task 359) — `/projects/{v2,legacy}/[projectId]/files` accepts `?folder=<folder uuid>` (opens that folder) and `?file=<asset uuid>` (opens the asset's own `folder_id`, then auto-opens its preview modal). `?file=` carries no companion `?folder=` on purpose — the folder is derived from the asset, so a moved file doesn't break the link. Unresolvable ids fall back to the Files root. Folder navigation syncs the URL via `window.history.replaceState`, **not** `router.replace` — both Files pages are `force-dynamic`, so a Next navigation would re-run the server component on every folder click. The copy URLs are built from `usePathname()`, never from the `projectId` prop: on v2 the `[projectId]` segment is the display `project_id` while the component receives the UUID. **Do not confuse this with the Onboarding Workspace's scheme** (`_workspace-url-params.ts`), which addresses folders by root-to-leaf *name* path (`?parent_folder=`/`?sub_folder_lN=`) because it maps deliverables onto folders; the workspace shares the same presentational `FilesTab` but omits the task-359 props, so it shows no Copy URL actions.

- **Projects classification navigation** (task 361) — classification switching for `/projects/v2` lives in the **sidebar's "Projects" nav group** (`v2-hub-sidebar.tsx`), not in the page itself: it expands to one link per `CLASSIFICATIONS` value plus **Legacy**, replacing the old flat "V2 Projects" / "Legacy Projects" pair (a task-361 follow-up correction — an in-page tab strip was tried first and removed once the intended target turned out to be the sidebar). The active classification is `?tab=<slug>` on `/projects/v2`, **not** a path segment: `/projects/v2/[projectId]` already owns that segment, so `/projects/v2/stackshift-i` would resolve as a project lookup. Slugs + helpers live in `src/app/(hub)/projects/_classification-tabs.ts`, whose `Record<Classification, ClassificationTabId>` map makes a new classification a compile error until it gets a sidebar entry. Bare `/projects/v2` and any unrecognized slug resolve to `stackshift-i` — so every existing link to `V2_ROUTES.PROJECTS_V2` (both dashboards, the `/portfolio-tracker` redirect, New/Import back buttons) lands on that tab. There is deliberately **no "All" link and no per-classification counts**. Because every classification child shares the `/projects/v2` pathname, `v2-hub-sidebar.tsx`'s active-link check (`isChildActive`) is query-aware — it resolves the current URL's tab via the same `parseClassificationTab()` the page uses and compares that, not a raw pathname match; a plain pathname child (Legacy, Tickets, Contacts, …) is unaffected. `_listing-shell.tsx` (the shared `/projects/v2` + `/projects/legacy` header) is title-only — no tab UI of its own; the active classification/count shows in the listing's own toolbar line instead. Classification tab membership is the union `customer_products.classifications[] ∪ customer_products.classification`, not the primary column alone, because three row shapes coexist: intake/import/order-convert rows write both, pre-task-157 rows have an empty array, and `PATCH /api/v2/projects/[projectId]/classification` used to write only the column (it keeps both in sync as of this task, via `mergeClassificationUpdate()` in `customer-phases.ts`). A multi-classified project therefore appears under **every** classification it carries. The `customer_products!inner` + `referencedTable` `.or()` join filter in `_load-list-data.ts` also excludes classification-less Zoho import noise by construction (task 272), retiring an unbounded `.is("classification", null)` lookup. `/projects/legacy` keeps its own route and listing; `/projects/v2/status-report` keeps its own separate client-side Classification filter.
