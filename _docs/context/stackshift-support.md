# StackShift direct support API and Desk poll

Moved verbatim from CLAUDE.md. Read before working in this area.

- **StackShift Support Center tickets live poll** (`POST /api/cron/desk-ticket-poll`, task 388) — StackShift (a separate app, `webriq-pagebuilder/app`) creates tickets directly in Zoho Desk via its own API integration (tagging every ticket `cf.cf_stack_shift_site`), on the **same Zoho Desk org** Central Hub already has API access to (`ZOHO_DESK_ORG_ID`). Until this task the only path that ever captured these was the one-time/manual `desk-tickets-import.ts` import; this cron closes the live gap going forward, one-way only (Hub reads Desk, never writes back — two-way sync explicitly deferred). Polls Desk's `/tickets/search?customField1=cf_stack_shift_site:${notempty}` (the exact filter StackShift's own app uses to scope "its" tickets), sorted `-modifiedTime`, against a cursor reusing the `email_poll_cursor` table's free-text `id` primary key (row `'stackshift-desk'`, migration 148) rather than a new table. Per ticket, pulls **both** the opening message (a Desk *thread* — Zoho auto-creates this from `POST /tickets`'s `description`) and every follow-up reply (Desk *comments*, not threads — StackShift's own conversation UI posts replies there); upserts into `inbox`/`inbox_messages` keyed by `external_id`, same column + convention `desk-threads-import.ts`/`desk-comments-import.ts` already use, author-type defaulting to staff/agent unless a comment's `commenter.type === "END_USER"` (mirrors those same import files, since most Desk comments are agent-authored). **The true end-user identity behind a StackShift-authored comment is not always recoverable** — StackShift correlates that separately via its own internal datahub API, which Central Hub has no access to; this poll displays whatever Desk itself returns. `inbox.channel` gained a 4th value, `'api'` (migration 148 widens the check constraint) — the existing `manual` value would otherwise mislabel a customer-filed StackShift ticket as staff-typed on the ticket detail page's Channel field (`_ticket-detail.tsx`'s `CHANNEL_LABELS` map renders it as "StackShift"). **Task 441 hardening:** `/tickets/search` is an *indexed* endpoint that lags hours to days (verified: a ticket created with the Site already set was not returned for 4 days though a direct fetch worked), so discovery is two-pass. The search pass (modified-time cursor, now with a 15-min overlap, `maxDuration = 300`, a 240 s run budget, oldest-first processing and a cursor written after **each** ticket, pure helpers in `src/lib/desk/poll-cursor.ts`) catches later edits; the **created-pass** (`runCreatedPass`, cursor row `stackshift-desk-created`, missing row = 7-day seed) lists newest-created tickets via real-time `GET /tickets?sortBy=-createdTime`, fetches each unseen one once for `cf` (List Tickets never returns it) and ingests StackShift ones, max 60 fetches/run. A Desk ticket that duplicates a Mail-poll ticket (helpdesk@ also feeds Zoho Desk; same requester, subject, created within ±1 h) is imported but flagged `source_meta.duplicateOf = { inboxId, ticketNumber }` and shows a banner on the detail page — never merged. **Zoho Mail poll:** `messages/view` returns newest-first only when `start` is passed (omitting it returned an old slice); `sortBy` accepts only `date`; listing now pages back until the cursor. A failed message stops the batch so the cursor can't skip it, messages store Zoho's `receivedTime` as `created_at`, and `src/lib/email/sent-ingest.ts` also ingests the Sent folder (`ZOHO_MAIL_SENT_FOLDER_ID`, cursor row `helpdesk-sent`) as staff messages on existing tickets only. Attachment ingestion for these tickets is explicitly deferred (StackShift's own attachment API is a distinct surface from Desk's `/tickets/{id}/attachments` that `email-poll` already knows how to download — not yet confirmed to resolve to the same underlying objects). **Attachments (tasks 392/457):** `syncTicketMessages()` stores thread, comment and ticket-level files; files on an attachment-only (empty-body) comment go to the opening message, never an empty message row (an extra empty Desk message would break parity's message count); the upload type goes through `correctedContentType()` (`@/config/attachment-types`): a missing/octet-stream/text-plain type, or `text/html` on a non-`.htm(l)` file (Zoho Desk's label for types it doesn't know, e.g. heic/webp/mp4), is replaced by the extension's type or `application/octet-stream`; `POST /api/admin/desk/repair-attachment-content-types` (admin, `?dryRun`/`?limit`/`?offset`, use `nextOffset`) relabels already-stored objects in place with the same rule; a failed download stamps `inbox.source_meta.attachmentSyncFailedAt` and each poll run re-syncs up to 10 stamped tickets (`runAttachmentRetries()`, `attachmentRetry` in the run log), giving up after 5 attempts (`source_meta.attachmentSyncAttempts`, reset when the Desk ticket changes). A comment whose insert failed keeps its files unassigned and counted as failed; only a genuinely empty body falls back to the opening message.

- **StackShift direct support API** (tasks 442/444/445, migrations 169 + 170 **written, not applied**) — StackShift's server posts tickets straight to the Hub instead of via Zoho Desk. Routes: `POST /api/webhooks/stackshift-support/v1/tickets`, `.../tickets/[ticketRef]/comments`, `.../tickets/[ticketRef]/status` (contract `_docs/plan/stackshift-hub-support-api-contract.md`, design `..-direct-support-design.md`, hand-off `..-handoff.md`). **Auth is HMAC, not a bare secret:** headers `x-ss-key-id` (`current|next`), `x-ss-timestamp` (±300 s), `x-ss-signature` = hex HMAC-SHA256 over `timestamp\nMETHOD\npath_with_sorted_query\nsha256(raw body)`; `STACKSHIFT_SUPPORT_SECRET` unset → 503, `_NEXT` enables zero-downtime rotation. Pure logic lives in `src/lib/stackshift-support/*-logic.ts` (no env/DB imports, so `npx tsx` checks run it); `auth.ts` verifies, `inbound.ts` is the shared pipeline (raw body → signature → 256 KB → zod `.strict()` → per-site Postgres rate limit 120/min → idempotency → write → `after()` audit), `create-ticket.ts` / `comment-status.ts` do the writes with `adminClient` (signed server, no Supabase session — same exception as the order webhook). **Rules that bite:** direct tickets get their **own** `inbox` row (`channel='stackshift'`, `external_ref` = StackShift's ref, `stackshift_site`, `desk_ticket_id`) and **never write `inbox.external_id`** (the Desk poll's upsert key). Correlation to the Desk copy is **exact** via `desk_ticket_id` ↔ `external_id`; both rows get `source_meta.duplicateOf { via:'desk_ticket_id' }` whichever arrives first (create endpoint flags the Desk row; `desk-ticket-poll`'s `processTicket()` flags the direct row via `findDirectTwin()`), exact beats the task-441 heuristic, and rows are never merged or skipped. Idempotency is `stackshift_idempotency` (key + route + body hash → stored response; replay = 200 `deduped:true`, mismatch = 409). `urgent` priority is stored as `critical`. Customer emails are **off** unless `STACKSHIFT_SUPPORT_NOTIFY_CUSTOMER=true` **and** the request's `suppressCustomerNotifications` is false. **Attachments (task 447):** bytes never pass through a handler — `POST .../v1/uploads/sign` (strict manifest, ≤10 files, ≤25 MB, `attachment-types.ts` allowlist; 422 type / 413 size) mints signed upload URLs into the **`ticket-attachments`** bucket (not `project-assets`: the Inbox `file-url` viewer only signs from `ticket-attachments`; the shared storage helpers gained an optional `bucket` arg, default unchanged). Paths are `stackshift-support/<site-slug>-<hash>/<ticketRef-slug>-<hash>/<ts>_<rand>_<name>`, server-generated and opaque to StackShift (the hash of the exact string stops sites whose names differ only by punctuation, e.g. `a/b` vs `a_b`, from sharing a prefix and registering each other's uploads); the `attachments` array on create/comment is verified (`verifyUploadedObject` magic-byte check, path must belong to that site + ticketRef, path not already registered) **before any row is written** — a bad file fails the whole request with 400 `details.path` and creates nothing — then inserted as `attachments` rows (`entity_type='inbox_message'`, `external_id` = path). Orphaned uploaded-but-unregistered objects are an accepted trade-off (task 339 precedent), no sweeper. Task 457: at registration `verifyRegistered()` reads each new object's `info()`; a stored type that differs from the extension's (StackShift PUT without `Content-Type`) is re-uploaded with the right type and logged with the site, and `attachments.size` is the real stored size, not StackShift's declared one. Neither step can fail the request. Outbound: `mintDownloadUrls()` signs fresh 15-min URLs from `attachments` rows at dispatch time and in `GET /events` (never stored in the outbox); the Hub has **no staff attachment upload** yet, so reply events only carry attachments when such rows exist. **Reads (task 448, migration 172 written, not applied):** signed `GET .../v1/tickets?site=&status=&userRef=&cursor=&limit=` and `GET .../v1/tickets/[ticketRef]?site=` through `handleSignedGet()`. `read-model.ts` is the pure allowlist layer (serialisers build every response field by hand — never spread a row — so internal notes, `source_meta`, staff emails/ids and customer-view password data cannot leak; leak-proof fixture in `_docs/task/448-read-model.check.ts`). The list is keyset-paginated on `(created_at, id)` DESC; the cursor carries the DB's **exact timestamp string** (a JS `Date` would drop microseconds and skip/repeat rows) and is validated before it is interpolated into the PostgREST `.or()` filter. `messageCount`/`lastMessageAt` come from the `stackshift_ticket_message_stats()` RPC (degrades to zeros if 172 isn't applied). **A ticket not found for the caller's site — including another site's — is a 404** (existence never leaks on reads; writes still return 403). Scope is `channel='stackshift'` only, so Desk-polled rows are invisible to these endpoints until cutover. Status is the raw Hub value (`open|on_hold|escalated|closed`, the user's choice — `escalated` is internal wording customers will now see). Activity = created + public messages + staff status events from the outbox + `inbox.source_meta.customerStatusLog` (capped 50, appended by `setCustomerStatus()`, since customer-initiated status changes are not outbox events). **Parity gate (task 449, migration 173 written, not applied):** `/desk/stackshift-parity` (admin/super_admin) is the ONLY evidence that unlocks the Desk step-down (task 450). `parity.ts` loads a site + window (default start = the site's first direct ticket, max 90 days / 2,000 tickets — a clamped or truncated report cannot be signed) and `parity-logic.ts` (pure, `_docs/task/449-parity.check.ts`) evaluates six checks: (a) every Desk-polled ticket (`source_meta.source='stackshift-desk-poll'`, site from `source_meta.stackShiftSite`) has a direct row via `desk_ticket_id`↔`external_id` — unacknowledgeable; (b) **customer-authored** public messages match by creation order on normalised HTML text (±2 min) — staff replies/internal notes are deliberately not compared because staff work one copy; (c) ticket-level attachment totals (Desk attaches all files to the opening message, so no per-message compare); (d) status + `resolved_at` — the only check that may be accepted per ticket with a written reason at sign-off; (e) no `dead` outbox events; (f) no 5xx on the site and auth failures ≤2% of API requests (auth failures carry no site, so they are counted API-wide). Thresholds are hard: ≥14 days AND ≥50 Desk tickets. Quirk: a Desk copy's `created_at` is the poll's ingestion time, so window membership for Desk-only tickets is approximate (pairs use the direct row's real time). Sign-off (`POST /api/desk/stackshift-parity/signoff`) **recomputes the report server-side** and refuses unless PASS, the typed site name matches and all three manual attestations are true; it writes `stackshift_parity_signoff` (service role only — no insert policy) and notifies the other admins; revoke needs a reason. Task 450 must require `latestSignoff(site)` to be non-revoked. Alerts: `POST /api/cron/stackshift-alerts` (every 10 min) notifies admins (in-app + push; Cliq call kept but disabled in code) on >10 failed auths from one key id (1 h cooldown, dedupe rows in `email_poll_cursor`) and on newly dead outbox events. **Desk step-down (task 450, migration 174 + two manual scripts, written, not applied — shipped DARK):** nothing changes until a site has a non-revoked parity sign-off. (1) **Reconcile mode** in `desk-ticket-poll`'s `processTicket()` needs BOTH `STACKSHIFT_DESK_RECONCILE_ENABLED=true` AND the ticket's site (`cf` Site, via `activeSignedOffSites()`) to be signed off; `reconcileDecision()` (pure, `stepdown-logic.ts`) then **refreshes** Desk rows the Hub already holds (design D5), **skips** retired copies and tickets whose direct copy exists, and records anything else as a **miss** in `stackshift_reconcile_misses` — it never imports on its own (a miss is a customer ticket the direct path lost). Misses are imported only via the admin-only `{importDeskTicketId}` branch of the poll route (`importMiss()`, reconcile off) or dismissed, from `/desk/stackshift-stepdown`. Revoking a sign-off returns the site to normal ingestion on the next run; a missing site custom field or an unreadable sign-off table also falls back to normal ingestion. (2) **Customer emails (D4)** use `shouldNotifyCustomer()`: request not suppressed AND site signed off AND (global `STACKSHIFT_SUPPORT_NOTIFY_CUSTOMER=true` OR site in `STACKSHIFT_SUPPORT_NOTIFY_SITES`, `*` = all signed-off); applies to ticket-created and staff-reply emails. (3) **Manual scripts** `supabase/manual/stackshift-stepdown/step-3_lower-desk-poll-cadence.sql` and `step-6_unschedule-desk-poll.sql` lower then unschedule the `stackshift-desk-ticket-poll` cron, each aborting unless a non-revoked sign-off exists. They are deliberately **not** in `supabase/migrations/`: `supabase db push` and branch deploys apply that folder automatically and in order, so a guarded script that aborts by design would fail the deploy and block every later migration — run them yourself in the SQL editor (see that folder's README). Never put a script whose precondition can legitimately be unmet into the migrations folder; 176 also aborts while open Desk-only tickets remain (override: `set local app.stackshift_force_unschedule = 'on'`). (4) **Duplicate cleanup (D6)**: `_docs/task/450-duplicate-cleanup/dry-run.ts` plans only (refuses without a sign-off) and writes `plan.json` + `apply.sql` + `rollback.sql`; apply is additive (`source_meta.fromDesk` on the direct row, `source_meta.retiredInto` on the Desk copy — nothing deleted/closed) and the Inbox list hides retired copies unless `?retired=1`. The operator runbook (order, verification, rollback; Desk channel and StackShift-side steps live outside the repo) is `_docs/plan/stackshift-desk-stepdown-runbook.md`. The earlier `shouldNotifyCustomer` in `inbound-logic.ts` was removed in favour of this gate. **Review hardening (final StackShift review):** (a) the three StackShift cron routes (`desk-ticket-poll`, `stackshift-outbox`, `stackshift-alerts`) authorise via `authorizeCronOrStaff()` (`cron-auth.ts`: timing-safe `x-cron-secret` OR a signed-in admin/super_admin/pm) — the older "any session" check let a `client`-role user trigger polls/dispatch/alerts, so use this helper for any new StackShift cron route; (b) `normalizeHtml()` is linear-time (hand-rolled `removeBlocks`/`stripTags` scans — the former lazy regexes were quadratic on crafted bodies, ~2 s per 112 KB; the adversarial-input timing checks in `449-parity.check.ts` guard it); (c) a create whose `ticketRef` already exists for the **same site and subject** returns `200 deduped` with the existing ticket (`isSameCreateRetry()`), not 409 — covers a lost response when the idempotency row never got stored; (d) contact lookups on a requester email use `escapeLike()` (`like.ts`) so `_`/`%` can't act as `ilike` wildcards and attach the wrong customer (the same unescaped pattern still exists in the non-StackShift `email-poll`); (e) a retried comment never re-verifies attachment paths its message already owns (`verifyUploadedObject` deletes the object when its read-back fails); (f) `stackshift_rate_limit_hit()` prunes expired windows only on a window's first hit (`count = 1`, backed by an index on `window_start`) rather than on every request; (g) generated task output under `_docs/task/*/out/` (e.g. the duplicate-cleanup `plan.json`, which carries real ticket metadata) is git-ignored — review it locally, never commit it. Audit/outbox/rate-limit/SLA tables come from 169 (`support_sla_config` is admin-editable). Verify without the StackShift app: `npx tsx _docs/task/445-support-harness.ts --base http://localhost:3000` (needs the migrations applied and a throwaway `STACKSHIFT_SUPPORT_SECRET` in `.env.local`). The existing Desk flow is untouched until the parity gate (task 449/450). **Outbound (task 446, migration 171 written, not applied):** staff actions on `channel='stackshift'` tickets become `stackshift_outbox` events delivered as HMAC-signed POSTs to `STACKSHIFT_EVENTS_URL` (`STACKSHIFT_EVENTS_SECRET`). A **public staff message** is enqueued by the `stackshift_enqueue_staff_reply` SQL trigger in the same transaction (PostgREST can't wrap two inserts) — so never insert a staff reply on a direct ticket without it being a real `inbox_messages` row; a **status change** is enqueued by `PATCH /api/desk/tickets/[ticketId]/status` via `enqueueStatusChanged()` (not a trigger, which would echo customer-initiated changes from the inbound API). `ticket.assigned` / `ticket.due_changed` have builders in `outbox-logic.ts` but **no emitter** (no assignee column / due-date UI exists). `POST /api/cron/stackshift-outbox` (pg_cron every minute) runs `dispatchDue()`: optimistic lease claim, strict per-ticket order via `selectDeliverable()` (only the lowest pending sequence of a ticket goes out; `dead` unblocks), 10 s timeout, initial + 5 retries (1 m/5 m/30 m/2 h/12 h) then `dead` + Cliq alert (note `sendCliqNotification` is globally disabled by `CLIQ_NOTIFICATIONS_ENABLED=false`, so the alert is currently a log line). Payloads are re-filtered through the `redactData()` allowlist at send time; a no-op when the events URL/secret are unset (events stay pending). **Replay** (admin/super_admin, `/desk/stackshift-outbox`) keeps the original `sequence`, so the receiver must apply events by sequence. Staff replies on direct tickets bypass Zoho Mail (`replyOnDirectTicket()`); the Hub only emails the customer when `STACKSHIFT_SUPPORT_NOTIFY_CUSTOMER=true`. Re-sync: signed `GET .../v1/events?site=&afterSequence=` (shared `handleSignedGet()` pipeline, reused by task 448). Test without StackShift: `npx tsx _docs/task/446-mock-receiver.ts --secret <s>`. **Transport hardening (task 452):** `resolveEventsConfig()` (`events-config-logic.ts`, env wrapper `events-config.ts`, checked by `_docs/task/452-events-config.check.ts`) fails delivery closed — events stay `pending`, one log line — unless `STACKSHIFT_EVENTS_URL` is plain https (http only for localhost outside production; no credentials/query/fragment). The events secret rotates like the inbound one: `STACKSHIFT_EVENTS_SECRET_NEXT` + `STACKSHIFT_EVENTS_KEY_ID=current|next` select which secret signs and what `x-ss-key-id` the Hub sends (`next` without the secret disables delivery). **Authorization is by `site` only** on `GET /tickets/{ref}` and the comment/status/uploads-sign routes — `userRef` only narrows the list — so StackShift must enforce per-user access itself; the StackShift-side rules are in `_docs/plan/stackshift-app-hub-integration-instructions.md`.
