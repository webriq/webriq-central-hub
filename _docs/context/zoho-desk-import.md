# Zoho Desk / Projects imports

Moved verbatim from CLAUDE.md. Read before working in this area.

- **`issues` table** (migration 051) holds imported Zoho Project Issues/Bugs — `project_id` FK required, `task_id` FK exists for future Issue↔Task linkage but is **always `null` from the import** (`zoho-import/issues/route.ts`); no Zoho export currently carries that linkage data. `severity` keeps Zoho's own vocabulary (`None|Minor|Major|Critical|Show stopper`), not the task `priority` enum. Import-only — no Issues browsing UI exists yet. `display_id` (migration 089/task 189) is a Hub-native, display-only human-readable ID (`<owning project's project_id with "-PROJ-" stripped>-I####`, e.g. `BDD824C501-I0001`, 4-digit per-project incremental sequence, `BEFORE INSERT` trigger + one-time backfill) — separate from and does not overwrite `prefix` (Zoho's own imported format, e.g. `"TC3-I1"`), since the two coexist in incompatible formats depending on row origin. `tasks.display_id` mirrors the same scheme with a `-T####` marker and its own independent per-project counter; both are shown in UI text only, never wired into routing.

- **`issue_comments` table** (migration 052) holds imported Zoho Issue Comments — `issue_id` FK required (not `task_id`; deliberately its own table, not merged into `task_comments`, since that table's `task_id` is `NOT NULL` and its RLS carries live author-insert semantics this import-only table doesn't need). Has `updated_at` (unlike `task_comments`, which has none) — real data showed ~11% of comments get edited after creation, worth tracking. `reactions`, `third_party_service_details`, `last_modified_by`, `can_edit_comment`/`can_delete_comment` are intentionally never stored (measured zero value from the real export). Comment attachments are metadata-only in `source_meta` — actual file retrieval before Zoho decommission is a separate, not-yet-scoped follow-up. Import-only, no live commenting UI.

- **`accounts` table** (migration 125 / task 335) holds imported Zoho Desk accounts (companies) from `_from_zoho/desk-accounts.json` (~6,143 rows) — `external_id` unique (Desk account id, the upsert conflict key), `customer_id` nullable FK → `customers` filled by the same normalized-name soft match the `contacts` import uses (`match_method` `'account_name'` | `null`; unmatched rows import anyway — most are CRM noise). Full raw Desk object kept in `source_meta`. Import: `POST /api/admin/zoho-import/desk-accounts` (`importDeskAccounts()` in `src/lib/migrate/desk-accounts-import.ts`), registered as the `desk-accounts` import level in the migrate tab; the `desk-accounts` *export* level already existed. Surfaced under **Desk → Contacts** (`/desk/contacts`), a two-tab directory (Contacts | Accounts, `?tab=`) with Tickets-style server pagination + search; detail pages `/desk/contacts/[id]` and `/desk/accounts/[id]` (both routed by UUID `id`) show related contacts/tickets. Sidebar "Desk" is a collapsible parent (Tickets, Contacts) — the sidebar's per-item `expanded` map (keyed by label) generalizes what was a single `projectsExpanded` boolean.

- **`kb_articles` table** (migration 126 / task 336) holds imported Zoho Desk **Knowledge Base** articles from `_from_zoho/desk-kb.json` — `external_id` unique (Desk article id, upsert conflict key), full HTML body in `answer`, plus `status`/`category_name`/`tags`/counts columnized and the whole raw article in `source_meta`. No customer matching (KB is global content). Export: `GET /api/admin/zoho-export/desk-kb` (`desk-kb` export level) writes `{ articles, categories }` — List Articles omits `answer` so each article gets a per-article Get Article pass (`enrichArticlesWithBody()` in `src/lib/zoho/desk.ts`, sibling of `enrichTicketsWithCf()`), `permission=all` pulls drafts/unpublished. Import: `POST /api/admin/zoho-import/desk-kb` (`importDeskKb()` in `src/lib/migrate/desk-kb-import.ts`). **Needs OAuth scopes `Desk.articles.READ` + `Desk.settings.READ`** (the latter only for the category list — a missing `settings` scope degrades to `categories: []` without failing) — regenerate `ZOHO_REFRESH_TOKEN` with them added (see `env.example`). `fetchAllDeskPages()` gained an optional 4th `extraParams` arg for `permission=all`. No KB browsing UI; `kb_categories` table deferred (article rows carry `category_name`/`category_id` inline). `desk-kb.json` is a JSON **object** not an array — the import route reads it via `readFromZohoObject()`, not `readFromZoho()`.

- **`tickets.source_meta.cf`** (task 329) holds the imported Zoho Desk ticket custom fields verbatim (`{ cf_<slug>: value }`), populated by the Desk Tickets export's per-ticket Get Ticket enrichment pass (List Tickets never returns `cf`). The live portal has exactly three ticket custom fields — `cf_white_label` (289 populated; actually holds the client/business name, e.g. "Quandary Consulting Group" — shown in the ticket UI under the label "Business Name", task 330), `cf_stack_shift_site` (224), `cf_service_type` (0, unused). `source_meta.whiteLabel` / `.stackShiftSite` are convenience promotions, resolved by normalized field-name match (`resolveCfField()` + `CF_TARGETS` in `src/lib/migrate/desk-cf.ts` — shared by the import and the task-334 backfill) so a Zoho label edit that shifts the slug still resolves. Surfaced on the ticket detail page (task 330). **Archived tickets** get `cf` too as of task 334 — the `desk-archived-tickets` export now runs the same per-ticket Get Ticket enrichment (`enrichTicketsWithCf()` in `src/lib/zoho/desk.ts`, shared with the live export), and `POST /api/admin/desk/backfill-archived-ticket-cf` (admin, SSE, `?dryRun`/`?limit`/`?ticketNumber`/`?force`) patches `source_meta.cf` in place for archived rows imported before that. A re-import from a pre-task-334 `desk-archived-tickets.json` would re-null `cf` — re-export first, or don't re-import.
