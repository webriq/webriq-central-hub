# Drive, Share Picker, Notes sharing

Moved verbatim from CLAUDE.md. Read before working in this area.

- **Personal Drive** (task 436, migrations 166 + 167 **written, applied by the operator** — 167 fixes the select policies so `insert … returning` works: STABLE policy functions can't see the row being inserted, so select policies must also grant by `owner_id`/parent access) — `/drive` (sidebar label `DRIVE_LABEL` = "Drive", Knowledge group) gives every **staff** role (`admin|super_admin|pm|developer|hr|marketing`; `client` blocked at the page, every `/api/drive/*` route and RLS) a private tree of folders + files, in two sections inside one page: **My Files** and **Shared with me** (`?view=mine|shared&folder=&file=`, URL synced with `replaceState`). **Deliberately NOT `customer_assets`** — that table's `customer_id` is `NOT NULL`, its RLS is "any authenticated", and `allowed_roles/allowed_user_ids` mean **NULL = everyone** (the inverse of a personal drive). Tables `drive_folders` / `drive_files` / `drive_shares` + private bucket `user-drive` (200 MB; all access via server-signed URLs, no `storage.objects` policies). **No share row = only the owner**; a folder share (user **or** role, `view`|`edit`) is **inherited by every descendant**; there is **no admin/super_admin override**. Access = `security definer` SQL helpers `drive_folder_level()` / `drive_file_level()` (3 owner · 2 edit · 1 view · 0 none; walk the parent chain) used by every policy; `src/lib/drive/levels.ts` is the pure TS mirror used to annotate rows in one pass — keep the two in sync. A non-owner editor may rename/delete a folder only when they hold edit on its **parent** (never the shared root itself), may delete a file only via edit on its folder, and a direct file-level `edit` share means **rename only** (the `PATCH` route restricts moves; RLS can't compare old vs new `folder_id`). Triggers keep `owner_id` immutable and a child's owner equal to its parent's, so an editor can never re-home an item into another tree. Upload = task 350's browser-direct signed-URL flow (`POST /api/drive/upload/sign` → XHR PUT → `POST /api/drive/files`, which verifies the object exists); the storage path is `<folderOwnerId>/<ts>_<rand>_<name>`, server-generated. MIME allowlist = `ALLOWED_MIME_TYPES` + PowerPoint + **drive-only audio/video recordings** (`DRIVE_MEDIA_MIME_TYPES` in `src/lib/drive/constants.ts` — keep it, `DRIVE_UPLOAD_TYPES` and the bucket's `allowed_mime_types` in lockstep); preview plays them in a native `<audio>/<video>` shell (`_drive-preview.tsx`). UI reuses Project Files' generic modules by import through `src/app/(hub)/drive/_reuse.ts` (upload queue, actions menu, rename/duplicate modals, folder-upload tree, selection hook, previews) — **Project Files is untouched**; the pieces that hard-code customer URLs or permission semantics (`_file-tile`, `_folder-tile`, `_use-bulk-download`, `_permission-picker`, `_files-toolbar`, `_use-folder-upload`) have Drive twins in `drive/`. Click on a Drive tile **opens** it (selection is the checkbox) — the opposite of Project Files' click-to-select. Hard delete, no trash; folder delete collects the subtree's Storage paths first (`collect-subtree.ts`) then removes them best-effort after the row delete. **Share notifications (task 437):** a new share, or a `view`→`edit` upgrade, sends each recipient an in-app notification (`event_type` `drive_share`, deep link `/drive?view=shared&folder=|file=`, + web push via `createNotification`) and a personal email (`src/lib/email/drive-share-notification.ts`; copy shared via `src/lib/drive/share-copy.ts`). A role share notifies every **current** member (resolved at share time, sharer + `client` excluded, `src/lib/drive/resolve-recipients.ts`); downgrades, removals and same-permission re-shares are silent; no opt-out in v1 (`notification_preferences` not consulted). Runs via `after()` from `scheduleDriveShareNotice()` (`notify-share.ts`) so it never delays or fails the share; missing `MAIL_*` skips email with one warning. Not built (follow-ups): trash/restore, per-user quota, share links, orphaned-object sweep after a user is deleted. The page probes `drive_folders` and renders a setup note instead of a raw PostgREST error while migration 166 is unapplied.

- **Share Picker** (task 438, `src/components/share-picker/`) — the one recipient picker for every file/folder-sharing surface: Drive's Share dialog, Project Files permissions (file/folder inline panel, bulk Share, Access tab) and the Notes folder-share dialog + note collaborator picker. A controlled, searchable multi-select combobox (`SharePicker`: `roles`, `people`, `value {roles,userIds}`, `onChange`, `excludeRoles`, `excludeUserIds`, optional `emptyLabel`): selected roles/people are chips in the field (role = navy pill, person = neutral pill with initials avatar), roles are toggle chips at the top of the menu, people are rows below. **Rules (pure, in `share-picker-logic.ts`, checked by `_docs/task/438-share-picker-logic.check.ts` via `npx tsx`):** selecting a role **hides its members** from the people list and drops already-picked members from the chips; deselecting restores them (not re-picked); already-shared roles/people are excluded by the caller; people already covered by an *existing* role share stay pickable (they may need a higher permission). **Placement (`use-anchored-menu.ts`):** the menu is portaled to `document.body` with `position: fixed` (no ancestor `overflow` can clip it), renders invisibly first, then — decided **once per open** — goes **upward** only when its real height doesn't fit below and there's more room above; max-height is clamped to the chosen side and coordinates follow the field on scroll/resize. Menu is `z-[70]` (above modals `z-50` and `ConfirmDialog` `z-[60]`); an enclosing anchored panel marks nested menus via `NESTED_MENU` (`[data-share-picker-menu]`) so clicks/Esc inside the nested menu don't close the outer popover. The picker only changes **how** recipients are chosen — Drive batch-shares at one permission (`useDriveShares.addMany`, one POST per target, 4 at a time, failed targets stay selected), Project Files keeps its semantics (empty = "All roles", every change applies immediately, `permissionSummary()` unchanged), Notes keeps its Share (n) flow. **People data:** pass `avatarUrl` (`profiles.avatar_url`; initials avatar is the fallback when absent/broken) and `inactive` (deactivated — `hub_users.status = 'inactive'`, task 378, via `getInactiveHubUserIds()`) on each `SharePerson`; inactive people are never offered but still resolve for existing chips/access lists, so data sources **flag** them (`/api/drive/people`, `/api/staff-directory`) instead of dropping them (Notes' `allMembers` comes from `getAssignableMembers()`, which already excludes them). Do not add a second recipient picker; extend this one.

- **Project Notes sharing has two axes** (per-note + per-folder). Per-note: `note_collaborators` (migrations 120/121) — an explicit collaborator sees a note regardless of `visibility`. Per-folder (migration 127 / task 337): `note_folders.visibility` (`private`|`public`) + `note_folder_shares` (each row targets exactly one of a `user_id` OR a staff `role` in `pm|developer|admin|super_admin`, at `view`|`edit`). `notes.visibility` (`private`|`public`, default `private`) is the per-note opt-in — a folder's audience (its shares, or all-staff for a `public` folder) can only ever see a note when that note's own author flipped it `public`; a folder share never exposes a `private` note. Public-folder all-staff access is **view-only**; folder-share `edit` grants note edit (title/content/color/pin/archive) but never delete. Folder-share management is gated to the folder's `created_by` / `admin` / `super_admin` (same as rename/delete). Enforced by RLS via `security definer` helpers `is_note_folder_manager()` / `can_access_note_folder()` (migration 121 anti-recursion pattern). Still staff-only — no policy widens notes to `client`/`marketing`. Migration 127 is **written, not applied** by the agent (Notes-migration convention, tasks 120/121/311); the folders `GET` degrades to a bare select until it lands.
