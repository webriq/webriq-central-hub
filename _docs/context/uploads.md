# Uploads and attachments

Moved verbatim from CLAUDE.md. Read before working in this area.

- **Route handlers accepting large request bodies** (e.g. multipart file uploads) need `experimental.proxyClientMaxBodySize` in `next.config.ts`, not `experimental.serverActions.bodySizeLimit` — the latter only governs `"use server"` Server Actions. Next.js 16's `proxy.ts` buffers the whole request body in memory and silently truncates past 10MB by default (no error to the client, just a corrupted body downstream). Requires a dev server restart to take effect. **But this only helps in local dev:** in production (Vercel) the platform gateway 413s any Route Handler request body over ~4.5 MB (`x-vercel-error: FUNCTION_PAYLOAD_TOO_LARGE`) *before the handler runs*, and no `next.config` value raises that cap. For anything a user might upload above ~4.5 MB, don't route the bytes through a handler — upload the file **browser-direct to Supabase Storage** via a signed upload URL. Task/issue attachments do this (task 339): `POST .../attachments/sign` runs the auth/permission/type/size/count checks and mints the URL (`createAttachmentUploadUrl()` in `src/lib/uploads/attachment-storage.ts`), the browser PUTs the bytes straight to Storage (`uploadViaSignedUrl()` in `projects/_shared/_attachment-dropzone.tsx`, kept as raw XHR for progress), then `POST .../attachments` verifies the object via a 64 KB ranged read (`verifyUploadedObject()`) and inserts the `attachments` row. Comment attachments still use the old multipart `uploadFileWithProgress()` path — follow-up. Trade-off of the direct-upload flow: a Storage object can be orphaned (uploaded, but the browser never reaches the register `POST`) — bounded by per-entity timestamped paths + the 200 MB bucket limit, no UI ever shows it; a periodic sweep of unreferenced `issues/`/`tasks/` objects is a not-yet-built follow-up. **Customer assets** (project **Files** tab, onboarding-workspace Files tab, Customers → Assets tab) use the same pattern as of task 350: `POST /api/customers/[customerId]/assets/upload/sign` runs the auth/write-role/MIME/25MB checks and mints the URL (`createCustomerAssetUploadUrl()` in `src/lib/uploads/customer-asset-storage.ts`), the browser PUTs to the private `customer-assets` bucket (`uploadViaSignedUrl()` in `projects/v2/[projectId]/onboarding-workspace/_upload-queue.tsx`), then the existing `POST /assets` register call creates the `customer_assets` row (now asserts `file_path` starts with `${customerId}/`). No content verification on this path (never had one). The legacy multipart `POST .../assets/upload` route stays for `projects/v2/[projectId]/_onboarding-wizard.tsx` (its own inline helper, 6+ call sites) — migrating it + a customer-assets orphan sweep are follow-ups.

- **Presentation uploads** (task 418) — `.ppt/.pps/.pptx/.ppsx/.odp` are defined once in `src/config/powerpoint-types.ts` and spread into each upload surface's own (still independent) allowlist: task/issue attachments (`attachment-types.ts` + `verify-file.ts`), customer assets, onboarding form, comment attachments, StackShift order uploads. **Wiki and `api/kb/upload` deliberately do not allow them.** Buckets `customer-assets`/`onboarding-assets` enforce `allowed_mime_types` themselves — migration 158 (**written, not applied**) appends the types; a new allowed type needs a bucket update too.

- **Task/Ticket attachment indicator** (task 459, migration 178 **written, not applied**) — a read-only paperclip + count (`AttachmentIndicator`, `projects/_shared/_attachment-indicator.tsx`, variants `chip|row|card`) on project task/ticket detail headers (v2 + legacy) and List rows / Board cards. Count = own files + comment files, the same set the Attachments tab shows. Detail headers take the count from the panel's existing Attachments fetch (`onAttachmentsCountChange`), no extra query; listings get `attachmentCountById` from `getProjectDetailData()` via one session-client `project_attachment_counts(p_project_id)` RPC (`security invoker`, RLS decides). Before 178 lands the RPC errors, logs one warning and no indicators show. Listing counts refresh on page load only.
