# Programme: checklist tasks, kickoff, delay notes

Moved verbatim from CLAUDE.md. Read before working in this area.

- **`tasks.kind` / `tasks.checklist_key`** (migration 163 / task 434, **written not applied**) — the StackShift I Phase 1 onboarding checklist (the 14 `INTERNAL_DELIVERABLES`) is mirrored as `tasks` rows with `kind = 'checklist'` (`checklist_key` = the config key, unique per project), attached to the Phase 1 `project_phases` row and the Phase 1 sub-phase deliverable (`milestone_id`/`tasklist_id` until task 430's rename). Checklist rows are **never listed or counted as tasks**: every task listing/count goes through `excludingChecklist()` (`src/lib/tasks/exclude-checklist.ts`), which applies `.eq("kind","task")` and silently retries unfiltered if the column doesn't exist yet (Postgres `42703`) — wrap any new task listing the same way. RLS keeps the legacy table's access: admin/super_admin/marketing read + write, pm/developer **read-only** (restrictive insert/update/delete policies; marketing has a checklist-only policy). `onboarding_internal_deliverables` is **dual-written and still authoritative** during the soak: `PATCH .../internal-deliverables/[key]` writes both (`syncChecklistTask()` is update-only — it never creates a lone row), seeding inserts both (`insertChecklistTasks()`, non-fatal), and `GET .../programme` reads `tasks` when the project has checklist rows else the legacy table (`loadInternalDeliverables()`). Mapping/adapter/planner live in `src/lib/programme/checklist-{tasks,store,backfill,backfill-sql}.ts`; existing projects are backfilled by the read-only dry run in `_docs/task/434-backfill/dry-run.ts` (writes a reviewable `out/backfill.sql`, never applies). The PM dashboard's Intake checklist card still reads the legacy table directly until the contract task drops it.

- **Programme kickoff + delay notes** (task 455, migration 177 **written, not applied**). `projects.programme_started_at` is the PM-confirmed kickoff. Tagging an already-started programme to another phase (`PATCH .../programme/phase`, `.../generic-phase`) **no longer backdates it**; only a first start does. Views read the current phase from the `active` row and fall back to the calendar window only when no row is active (the Customers list badge included). Change a kickoff only via `PATCH /api/projects/[projectId]/programme/kickoff` (admin/super_admin/pm, `YYYY-MM-DD` stored as `T12:00:00Z` so it is Day 1 in every timezone, then `rematerialiseProgrammeDates()`), which is the Timeline's **Kickoff** editor. Bulk corrections go through `_docs/task/455-kickoff-rebaseline/dry-run.ts` (plan/apply/rollback, operator-applied). Delay notes: per phase (`phase_programme_state.delay_note`) and per project (`projects.delay_note`), each with `delay_note_updated_at/_by`. Writers are admin/super_admin/marketing/**pm** (pm unrestricted per task 291). Both note routes write **only** the note columns with `adminClient` after the role check, because the `phase_programme_state` RLS write policy deliberately stays admin/super_admin/marketing so PMs can't touch `wizard_data`/`override_note`. Pure rules: `src/lib/programme/note-rules.ts`; reads + 42703 fallback: `delay-notes.ts`. One editor, `DelayNoteEditor`/`NoteCell`/`ProjectNoteCell` (`status-report/_status-report-note-cell.tsx`), is used by the Status Report, the Status Summary drawer and the Timeline's `_programme-notes-bar.tsx`.
