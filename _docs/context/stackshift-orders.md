# StackShift orders and contact validation

Moved verbatim from CLAUDE.md. Read before working in this area.

- **`stackshift_orders` table** (migration 130 / task 347, **written not applied** by the agent) holds submissions from the public StackShift Order Form on webriq.com. A webriq.com **server-side proxy** relays each submission (never the browser directly — no CORS) to `POST /api/webhooks/stackshift-order`, secret-authed via the `x-stackshift-webhook-secret` header (`STACKSHIFT_ORDER_WEBHOOK_SECRET`, timing-safe; absent → 503). The two documents (required Proposal, optional FlowForge spec) upload signed-URL-direct to the `project-assets` bucket under `stackshift-orders/incoming/<uuid>/` via `POST /api/webhooks/stackshift-order/uploads` (reuses task 339's `createAttachmentUploadUrl`/`verifyUploadedObject`), sidestepping Vercel's 4.5 MB body cap. The webhook only **records + notifies** (`STACKSHIFT_ORDER_NOTIFY_EMAILS` fixed list ∪ every PM's email from `auth.users` ∩ `profiles.role='pm'`, sent via `mailer.ts`'s now-exported `transporter`/`FROM`) — it never creates customers/projects. Task 354: after a successful insert the webhook also sends a **customer confirmation email** to the submitter (`contact.email` ∪ `billing_email` when it differs) — `sendStackShiftOrderCustomerConfirmation()` in `src/lib/email/stackshift-order-customer-confirmation.ts`, a receipt with the selected services + "what happens next", **no** internal review link, `replyTo` from `STACKSHIFT_ORDER_REPLY_TO` → first notify-list entry → omitted. It runs in its own `try/catch` independent of the staff notification (a failure in either doesn't suppress the other; neither fails the `201`), is skipped when `contactRisk === "high"`, and stamps `customer_notification_sent_at` (migration 135, **written not applied** — the stamp `update` is a wrapped no-op until it lands; surfaced as "Customer emailed {date}" in the `/stackshift-orders` list + review page). A proxy retry with the same `idempotencyKey` can't double-send — the dedupe early-return precedes both notification blocks. Staff review + convert happens at `/stackshift-orders` (`(hub)`, admin/super_admin/pm): `POST .../[orderId]/convert` mirrors the New Project intake's `save` mode — `generateCustomerId` (or link existing) + `upsertPrimaryContact` + one `customer_products` row + one **draft** `projects` row (no `seedAndStartProgramme`); `PATCH .../[orderId]` dismisses/reopens; `GET .../[orderId]/file?which=proposal|spec` signs a download. Form `services` → `customer_phases` CLASSIFICATIONS via `src/lib/stackshift-orders/service-map.ts` (`FlowForge` → `Discrete Development`). `src/lib/stackshift-orders/match-customer.ts` is an **advisory-only** existing-customer hint shown to the reviewer. webriq.com proxy contract: task 347 doc appendix. **`contact_risk`** (`low|medium|high|null`, migration 134 / task 353, **written not applied**) — the webriq.com proxy now runs the task-353 contact-validation check before relaying; a blocked submission never arrives, a borderline one is relayed with `contactRisk:"medium"` in the payload. The webhook stores it via a **best-effort follow-up `update`** (not the main insert) so a pre-migration-134 DB never fails the relay — `raw_payload` carries it regardless. Surfaced as an amber "Contact flagged" pill in the `/stackshift-orders` list + a header pill and warning banner on the review page (`ContactRiskPill` in `_order-ui.tsx`). **`submitter_ip` / `submitter_user_agent`** (`text`, nullable, migration 136 / task 356, **written not applied**) — the webriq.com proxy forwards the real submitter's client IP + browser UA in the payload as optional `submitterIp` / `submitterUserAgent` (the Hub is called server-to-server, so its own request headers are the proxy's, not the submitter's). Stored via another **best-effort follow-up `update`**, separate from the `contact_risk` one so each degrades independently pre-migration; `raw_payload` carries them regardless. No review-UI surfacing.

- **`validation_cache` + `validation_logs` tables** (migration 133 / task 353, **written not applied** by the agent) back `POST /api/public/validate` — the shared email/phone validation endpoint webriq.com (and later other WebriQ properties) call **server-to-server** (never the browser) before storing a lead/signup. Secret-authed via the `x-contact-validation-secret` header (`CONTACT_VALIDATION_WEBHOOK_SECRET`, timing-safe; absent → 503), same shape as the stackshift-order webhook. Wraps two Abstract products — **Email Reputation** (`emailreputation.abstractapi.com`) and **Phone Intelligence** (`phoneintelligence.abstractapi.com`) — each a consolidated superset that returns deliverability + quality + risk + breaches in **one** request (the legacy Email/Phone *Validation* products folded into them), each with its own env key + quota pool; an unset key fails that kind open. Logic lives in `src/lib/validation/`: `decision.ts` orchestrates cache → **one** Abstract call → hard-block check (bad format / undeliverable / disposable email / invalid phone) → `risk-score.ts` composite score (starts at 100, signals subtract; ≥70 low / 40–69 medium / <40 high → `allowed:false`) → cache write (30-day TTL, SHA-256-of-normalized-value key) → `validation_logs` row. Response is **only** `{ email?: {allowed,riskLevel,reasonCode}, phone?: {...} }` — never raw Abstract payloads, never a mailbox-level failure reason. **Fails open**: any Abstract outage/quota (`422`/`429`)/timeout → `{allowed:true, riskLevel:"unknown", reasonCode:"validation_unavailable"}` + `degraded` log + deduped Cliq alert. Cache/log DB calls are wrapped so the endpoint still works (uncached) before migration 133 lands. Request `stakes` is accepted but inert (the single call always returns full data). VoIP is flagged medium by default (`CONTACT_VALIDATION_BLOCK_VOIP=true` to hard-block). `GET /api/cron/validation-quota-check` (cron-secret or session) sums `validation_logs.abstract_calls` per product for the month and Cliq-alerts at 80% of `ABSTRACT_FREE_TIER_LIMIT` (default 100). webriq.com form handler + client-side zod/libphonenumber are **out of scope** — contract in task 353 doc appendix.
